## Prompt to paste into the audit task

Perform a blind, independent quality audit of a completed lower-model Taskledger run.

The implementation was generated by Luna/medium and reviewed by Terra/high. Your purpose is to measure defects that escaped that review. You are an evaluator, not an implementer.

Inputs:

- Repository: `<ABSOLUTE_REPOSITORY_PATH>`
- Approved specification: `<ABSOLUTE_SPECIFICATION_PATH>`
- Base commit: `<BASE_OID>`
- Frozen final commit: `<FINAL_OID>`
- Taskledger database: `<ABSOLUTE_LEDGER_DB_PATH>`
- Report destination: `<ABSOLUTE_AUDIT_REPORT_PATH>`

### Isolation rules

1. Confirm from runtime context that you are using `gpt-5.6-sol` with high reasoning effort. Report the observed model and effort.
2. Confirm the repository is on `<FINAL_OID>` and that the canonical worktree is clean. If either condition fails, stop without auditing and report the mismatch. Do not switch branches, reset, stash, commit, or clean files.
3. Do not read the implementation Codex task, its summaries, worker discussions, Taskledger submission summaries, verification decisions, rejection corrections, or prior benchmark conclusions before freezing your independent findings.
4. Do not modify source, tests, documentation, configuration, Git state, or Taskledger state. Do not send messages to the implementation task. Do not propose or apply fixes during the blind phase.
5. Inspect only the approved specification, repository state at `<FINAL_OID>`, the exact diff `<BASE_OID>..<FINAL_OID>`, relevant surrounding code, and tests you independently choose to run.
6. Treat test success as evidence, not proof. Review behavior, error paths, concurrency/state semantics, public API compatibility, security boundaries, documentation promises, and preservation/non-goal requirements explicitly.

### Phase A — blind review

Build a requirement/criterion checklist directly from the approved specification. Then:

- Inspect the exact base-to-final diff and all relevant surrounding implementation.
- Run proportionate independent verification against the frozen final commit.
- Check for missing behavior, incorrect behavior, regressions, weakened tests, deleted coverage, undocumented breaking changes, scope violations, and preservation failures.
- For concurrency, security, data integrity, or compile-time guarantees, verify that the implementation structure establishes the property rather than relying only on probabilistic tests.
- Record each finding before inspecting any Taskledger review history.

Classify findings as:

- `P0 critical`: unsafe to use or release; severe security/data-integrity/correctness failure.
- `P1 high`: material requirement failure, likely user-visible defect, or serious regression.
- `P2 medium`: real defect or meaningful coverage/documentation gap with bounded impact.
- `P3 low`: minor defect that is worth correcting but does not undermine the iteration.

For every finding include:

- stable identifier;
- severity;
- concise title;
- exact file and tight line location;
- violated specification requirement or acceptance condition;
- concrete technical evidence;
- an independently reproducible check when practical;
- confidence: high, medium, or low.

Do not count style preferences, speculative redesigns, or work explicitly excluded by the specification as defects.

Write and save the Phase A findings to `<ABSOLUTE_AUDIT_REPORT_PATH>` before continuing. The report must state explicitly when there are no findings. After saving it, do not alter the Phase A finding set or severities based on later review-history knowledge; append reconciliation separately.

### Phase B — review-history reconciliation

Only after Phase A is frozen, inspect the completed Taskledger ledger read-only. Use immutable database access or supported read-only Taskledger views. Do not invoke verification, integration, blocker resolution, operation resolution, plan mutation, or completion commands.

Record:

- tasks and requirements completed in this run;
- submission count and accepted/rejected/blocked outcomes;
- correction cycles by task;
- issues the Terra reviewer caught before integration;
- whether each Phase A finding was already caught and corrected, documented as accepted risk, or truly escaped into `<FINAL_OID>`.

A defect present only in a rejected intermediate submission is a **review catch**, not an escaped defect. A defect still present in `<FINAL_OID>` is a **review escape**, even if discussion mentioned it. Keep ambiguous mappings explicit.

### Final report

Append these sections to the frozen Phase A report:

1. Audit identity: repository, base/final OIDs, specification, audit task ID, model/effort, start/end timestamps.
2. Verification performed and exact results.
3. Frozen Phase A findings.
4. Taskledger reconciliation and review catches.
5. Escaped-defect table by severity.
6. Quality verdict:
   - `NON_INFERIOR`: no P0/P1 escapes, verification passes, and at most bounded P2/P3 issues;
   - `CONCERNING`: no P0, but at least one P1 escape or a pattern of material P2 escapes;
   - `FAILED`: any P0 escape, invalid frozen state, or required verification cannot pass.
7. Confidence and limitations, including weakly testable requirements.

Do not implement fixes. Return the report path and a concise verdict. Keep this audit's tokens separate from the lower-model run's operational usage; they are evaluation cost, not implementation/review cost.

## Measurement notes for the later comparison

Record the audit task ID and timestamps alongside the lower-model checkpoint. Compare:

- operational Luna/medium plus Terra/high tokens and credits;
- Sol/high audit tokens and credits separately;
- first-pass acceptance and correction rate;
- Terra review catches by severity;
- Sol-discovered escapes by severity;
- final verification result and quality verdict;
- elapsed operational time and audit time separately.

Report two cost views: lower-model operational cost alone, and operational plus shadow-audit cost. Do not convert token counts between model tiers; use exact cohorts and observed credits when available.
